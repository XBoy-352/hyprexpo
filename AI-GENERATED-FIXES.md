## Crash #1 (primary) — `std::bad_variant_access` in `Layout::CAlgorithm::recalculate`

### Symptom
Hyprland `SIGSEGV` when an (XWayland) window requests a fullscreen state change:

```
CXWM::handleClientMessage
  → CCompositor::setWindowFullscreenState
    → Layout::CLayoutManager::fullscreenRequestForTarget
      → Layout::CSpace::setFullscreen
        → Layout::CAlgorithm::recalculate
          → std::__throw_bad_variant_access      ← crash
```

The crash log tail also showed a **monitor hot-unplug (DP-1 disconnected)** happening around the
same time, i.e. a multi-monitor / output-change scenario.

### Hypothesis
HyprExpo never touches fullscreen directly. But to render the overview it temporarily makes each
previewed workspace the **preview monitor's** active workspace and forces a layout recalculation
(`activateWorkspaceForPreview` → `recalculateMonitor` + `CSpace::recalculate`). For a workspace that
actually lives on a **different** monitor, this recomputes its `Layout::CSpace` against the *wrong*
monitor. The suspicion is that this can leave the space's fullscreen/geometry bookkeeping (an
internal `std::variant`) in an inconsistent state, so a later **real** fullscreen request walks into
`std::get` on the wrong variant alternative → `std::bad_variant_access`.

### Speculative fix
After each preview tile is rendered and the preview monitor's active workspace has been restored,
**recalculate the previewed workspace once more** so it is re-synchronised to its own monitor's
context instead of being left computed against the preview monitor.

- New helper `resyncPreviewedWorkspaceLayout()` in `Overview.cpp` (declared in `OverviewInternal.hpp`).
- Called right after `restoreActiveWorkspaceAfterPreview()` in both preview render paths:
  - `Overview.cpp` (initial full render, `COverview` constructor)
  - `OverviewRender.cpp` (`redrawID`)

This is **additive and defensive** — at worst it is a redundant layout recalculation. It is *not*
proven to fix the crash.

## Crash #2 (secondary, related) — gesture re-entry `setValueAndWarp` crash (issue #57)

### Symptom
`SIGSEGV` in `COverview::onSwipeUpdate → CGenericAnimatedVariable::setValueAndWarp` when a touchpad
gesture is re-triggered while the overview is still closing/tearing down
(see <https://github.com/sandwichfarm/hyprexpo/issues/57>). This is a **different** crash from #1
and is **still open upstream**; included here only because it shares the same Hyprland version.

### Speculative fix
Null-guard the animated variables (`size`, `pos`) in `onSwipeUpdate()` and `onSwipeEnd()` in
`OverviewInteraction.cpp` before dereferencing them, so a swipe arriving during teardown bails out
instead of touching released animation state. This is conservative (it does not change the normal
close-animation behaviour) but is also **unverified** against the actual #57 reproduction.

## Crash #3 (the real repeat offender) — dangling monitor in the mouse-move callback

### Symptom
`SIGSEGV` inside `Hyprutils::Math::Vector2D::operator-`, called from the overview's cursor-move
callback, when the monitor the overview is open on is **unplugged**. Reproduced deterministically:
open the grid on an external monitor, then disconnect it.

### Root cause (confirmed, not speculative)
`addr2line` on the crashing `hyprexpo.so` pinned it to **`Overview.cpp:908`**:
```cpp
lastMousePosLocal = g_pInputManager->getMouseCoordsInternal() - pMonitor->m_position;
```
`pMonitor` is a **weak** reference (`PHLMONITORREF`). This input callback dereferenced it **raw** —
no `.lock()`. When the monitor is removed, Hyprland repositions the cursor (`CPointerManager::
closestValid → onMouseMoved`), which fires this callback; `pMonitor->m_position` then reads a freed
`CMonitor` and segfaults. Upstream's #50 added `pMonitor.lock()` guards across the overview, but
**this one input callback was missed.**

### Fix (high-confidence)
Lock `pMonitor` at the top of the callback and bail if the monitor is gone, then use the locked
`MON->m_position` — exactly the pattern used everywhere else in the file:
```cpp
const auto MON = pMonitor.lock();
if (!MON)
    return;
```
This is a textbook dangling-weak-pointer guard, not a guess — the addr2line line, the surrounding
`lock()` usage, and the crash backtrace all agree.
